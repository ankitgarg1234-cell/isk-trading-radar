## Acquisition schedule and handoffs — proposed, not enabled

1. Universe/identity: check entitled changes daily and before every decision; rebuild and compare the complete effective-dated snapshot at month-end. Never filter through today's survivors.
2. Calendar/status: verify the session before daily collection and before the proposed open; consume qualified halt/closure updates during an execution window. Incomplete status coverage holds the cycle.
3. SEC: proposed five-minute discovery polling during supported filing availability, with a single global limiter initially capped at one request/second. Discovery triggers original-accession retrieval, fact/context proof and an immutable handoff; it never overwrites a previous vintage. A deadline does not convert missing facts into a negative gate.
4. Market/actions: collect completed regular-session data after the official close, initially allow 15 minutes for delivery, then apply freshness/coverage checks before sealing. A missing deadline creates a hold. The next-open preview is produced only after its qualified open observation; a daily-bar start timestamp is not evidence of a completed close or an observed execution open.
5. B: acquire bounded batches grouped by original accession, starting with displacement-risk cases. Existing opt-in acquisition remains its separately documented bounded research process. No schedule is enabled here.
6. All collectors hand off source receipts to the vault and the normalizer; QA reads retained raw objects independently. Store exact bytes, safe URL without credentials, SHA-256, HTTP status/type, schema/provider version, request/completion/first-observed times, original event time/timezone, security/accession and historical coverage disposition. API secrets must be removed from URLs/logs and never reach the browser or repository.

Future acquisition retries follow the bounded design in [ARCHITECTURE.md](ARCHITECTURE.md). Transport/rate-limit failures may retry; hash, temporal, semantic or identity conflicts cannot auto-clear. Each request attempt has its own receipt. Unlicensed/unsupported sources and incomplete pagination result in HOLD with owner and next required evidence.

## Provider and time traps requiring explicit QA

IBKR's [historical-data guidance](https://interactivebrokers.github.io/tws-api/historical_data.html) explains that historical trade filtering can change volume relative to real-time observations. Qualify the applicable API/version, `whatToShow`/source, regular-hours definition, volume factor, bar timestamp meaning, corrections and split/dividend adjustment. The connector's supplied OHLCV and action arrays alone do not prove those semantics. Do not derive prior-day availability from a daily bar's opening timestamp or interpret a REALTIME snapshot status as an observed official opening-auction price.

[IBKR session documentation](https://www.interactivebrokers.com/docs/web-api/authentication/trading) associates subscriptions/permissions with usernames and constrains brokerage sessions. A continuously running collector requires an approved, independently scoped integration that does not interrupt existing live usage. This chat connector is a feasibility probe, not an operational worker or guaranteed historical archive. Only a method-and-endpoint allowlist for market/contract/metadata reads is permitted; deny order placement/modification/cancellation, order instructions, transfers and account/watchlist/alert writes, even if an underlying credential could otherwise do them. Do not initiate/reconfigure a session or gateway during this design work.

Yahoo baseline reproduction and independently sourced correction are separate evidence products. IBKR data that differs from the original vendor is not automatically erroneous. Frozen code parity on identical pinned inputs and independently reviewed new/corrected data are separate checks; do not force new data to reproduce wrong original inputs. Matching top-five outputs alone does not prove complete raw parity. Review and lock the complete adapter/rule mapping, including r63, nominal close, vendor-close × volume ADV and next-open execution. Unresolved mapping blocks G1; there is no fallback that buys using whichever feed succeeds.

## Source release acceptance

G1 requires access/retention rights, measured availability lag and coverage, full membership/identity lineage, raw original financial/publication evidence, removed-name prices/actions, session semantics, all pagination, separate adjustment vintages, deterministic frozen-rule parity and adversarial missing/future/correction tests. The source dashboard must display proposed/unconnected, historical sample, unresolved or certified coverage accurately; an HTTP 200 is never a certification status. G2/G3 and explicit user release remain separate gates.
